# P20 厂商转码源码核对（2026-09-21）

## 结论

完整读取 MakeP20BinOpenCV4(2).cs，并与统一版的 P20PolarMapper、P20BinEncoder、P20FfmpegPreparation 对照。此次文件与 (1).cs 内容完全一致，SHA256 均为 2F6F9B6E6637178018ACA6454C33A3106A39912CAFF8D88F6A5047224F928304。

确认一处可复现的移植差异并修复：简化三角公式的浮点运算顺序与厂商分象限公式不同，在固定种子随机RGB帧的460800个输出通道中有342个相差1。现改用厂商原运算顺序；同一独立对照测试所有通道一致。此微小颜色差异不是此前十几秒上传失败的已证实原因。

不能据此宣称“程序完全无误”：厂家给的是依赖其他类型的单个C#文件，未附完整可运行工程及P20TranscodeAsync实现；本轮没有运行原C#/OpenCV程序与本程序二进制逐字节比对，也未连接P20真机。

## 格式、映射及流程核对

| 项目 | 厂商行为 | App核对结果 |
| --- | --- | --- |
| 输入尺寸/帧率 | 构造函数fps参数未使用；前置转码在另一个未提供的方法中 | App明确归一化298×298、20fps，读取RGB24；不能推断厂商前置裁剪滤镜完全相同 |
| 时长 | frameCount×50，4字节小端 | 一致，单位实际是毫秒，源码“秒”注释不准确；不计两帧引导黑屏 |
| 引导帧 | 两帧160×960黑色JPEG，quality93 | 一致 |
| 采样表 | 中心149.5、半径l+0.5，最终坐标减1；960角度、149灯 | 保留分象限及求值顺序，独立全帧对照通过 |
| 行列 | frame.At(w,h)把w当行、h当列 | App没有按通常x/y理解交换轴 |
| 插值 | 每次线性插值转byte截断，再进行下一次 | 一致，不改成一次浮点双线性后统一四舍五入 |
| 通道 | OpenCV BGR读入并BGR写回 | App RGB读入并RGB编码，语义上保持红绿蓝而非原样交换字节 |
| 中心遮罩 | l=0仅i%16==0亮；l=1..7受i%8约束 | 一致；随机全帧对照同时覆盖遮罩与边缘 |
| 输出布局 | row=959-i、col=159-l；前11列黑 | 一致；输出宽160、高960并非普通298方形JPEG |
| 亮度 | 阈值149×3×128，float比例，rate_f在整个视频内只减不增 | App用float32比例及确定性最小值，白帧后黑帧不复位；新视频复位测试通过 |
| JPEG | 初始quality93；达到63×1024时从92往下降 | App遵循此阈值，quality下限1并在仍超限时失败；不同JPEG库不保证字节相同 |
| 降级亮度 | 初次编码mat×rate_f，但降低quality后改编码未调光mat | App当前保留此厂商行为，见风险说明，不擅自声称始终有亮度限制 |
| 帧记录 | 小端length + 1600零字节 + JPEG + 零填充 | 一致；length不含自身4字节，载荷四字节对齐 |
| 文件类型 | 自定义连续JPEG容器 | App传设备文件虽然用.mp4命名，但内容是该专用容器，不是直接上传普通MP4 |
| 异常处理 | 原源码直接写目标文件 | App采用partial文件成功后发布，取消/截断时清理，保留源素材 |

298×298是输入采样尺寸；160×960是硬件极坐标输出布局，两者不同不是转码尺寸错误。通讯帧长度用大端，视频容器长度用小端，不能混用。

## 厂商代码本身需要注意的地方

1. Parallel.For 内无锁更新共享 rate_f，比较与赋值不是原子最小值，结果可能受线程时序影响。App采用确定性最小值，不复制竞争条件。
2. JPEG质量降低路径跳过亮度缩放，可能使复杂明亮画面与简单画面的调光行为不同。若该阈值用于硬件功率保护，应由厂家确认是否应始终缩放；此次未擅改此格式行为。
3. “每帧<64K”注释与实际判断不完全一致：判断的是JPEG<64512字节，加1600预留区及对齐后完整记录可能超过65536字节。不能自行把JPEG限制当成整条记录限制；需厂家确认解码缓冲要求。
4. fps形参没有使用，lednum固定149，矩阵固定960×160但cor/led可外部传入。单个文件无法证明调用者总是传入适配值；App已固定该硬件规格。
5. IsSuccess没有在每次TransformBinAsync开始清零，重复使用实例可能残留前次成功状态；App没有使用这个状态实现。
6. 源码质量递减没有下界、前导Mat未显式Dispose、totalFrames依赖容器元数据，异常或取消可能留下半成品。App有质量下限、实际RGB帧数与原子输出，不复制这些缺陷。
7. OpenCV矩阵缩放的取整与Dart round在半整数边界可能不同，JPEG实现及平台数学库也可能不同。因此“未压缩映射样本一致”不等于“C#最终JPEG字节完全一致”。需厂商输出金样或完整工具作最终比对。
