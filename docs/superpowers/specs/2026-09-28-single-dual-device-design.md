# 同一 App 支持单列表与双列表 P20 设备

日期：2026-09-28。状态：用户已确认；软件实现完成，实机验收待执行。

## 目标与已确认要求

一个 App 连接并控制两种硬件，保留已经在 APK 实机验证的视频上传功能。

| 设备 | 用户提供的 Wi-Fi 示例 | 列表和音频能力 |
| --- | --- | --- |
| 双列表 | HILDORS_P20_123456 | 保留现有两列表及各自上传流程 |
| 单列表 | CS_P20_903642 | 一个视频列表，无音频播放能力，不抽取、不生成、不上传音频 |

## 方案选择

采用设备能力描述与协议适配层：复用界面和视频准备，按已验证的设备类型选择连接、命令和上传实现。

比较过的替代方案：直接把现有 `modernProtocol` 布尔判断扩散到所有页面，改动看似少，但容易让列表、音频和设置能力失配；为单列表复制完整 App，隔离简单，但会重复维护裁剪、转码与界面。推荐方案将差异限制在设备能力和协议适配边界，不重写已经有效的双列表传输。

## 连接与设备能力

增加明确的设备类型（未识别、单列表、双列表）及能力描述，包括列表数量、音频支持、文件规则和支持的控制命令。连接成功后的设备能力是页面和上传的唯一依据，不能仅依赖用户选项或文件名。

默认自动识别，优先探测现有双列表协议；识别失败后关闭该连接，再使用全新的 TCP 连接探测单列表协议。两者都使用只读亮度查询 0x04，以各自封装和回复规则严格校验，超时和无效帧不能算识别成功。单列表请求带 0x00 数据，双列表沿用现有请求形式。每次探测有界超时，可以取消；两个协议不会同时占用设备连接。

保留手动选择自动／单列表／双列表的入口。手动选择只限制探测类型，仍需校验设备回复。Wi-Fi 名称用作连接说明与辅助线索；本次不新增读取 SSID 的系统权限或插件，也不声称可凭名称自动可靠识别。

连接管理负责生命周期，不在活动连接上修改协议布尔值。更换设备时取消请求、关闭旧连接、清空设备状态和列表缓存，建立新的会话。使用连接代次丢弃旧回调。上传期间禁止自动探测和其他控制命令插入文件字节流；用户主动切换设备时结束当前上传，不跨设备自动续传。

## 界面与控制行为

双列表继续显示现有两个列表及其操作。单列表只显示一个视频列表，不显示切换列表、音频或不支持的蓝牙控制入口。播放、暂停、亮度、视频删除等按厂家确认的单列表命令执行。

能力判断覆盖首页、设备视频列表、上传入口、素材投放和设置，不能只隐藏一个页签。单列表不得发送现代协议的切换列表命令或格式化命令；恢复出厂等破坏性操作不在本次新增范围内，未适配入口保持不可用。断线后显示未连接状态，不能沿用上一台设备的列表或成功提示。

沿用已有列表会话和控制器中可验证的单列表分支，补齐回复长度、索引和状态校验，不把旧分支存在等同于已适配完成。

## 单列表上传协议

依据用户提供的《P20产品通信协议(1).docx》（正文标题为 P11产品通信协议）。设备归属按用户确认，不根据文件标题擅自更改产品定义。

- TCP 地址 `192.168.4.1:8900`；请求头尾 AA/A5，回复头尾 55/5A，长度为大端，CRC 字节固定 02。
- 0x31 上传请求为四字节大端文件长度与文件名，不带列表 ID；文件名含 `.bin` 后缀不超过 32 字节。
- 首期使用 App 生成的 ASCII 文件名，规避厂家未说明中文编码的问题。
- 0x00 表示准备好；之后每次发送一包，等待回复后再发下一包。厂家要求包长 35700 字节。
- 0x01 加四字节包序号表示传输进度；0x02 表示完成；0x80～0x85 映射为对应错误。
- 本地进度只按真实发送且已确认的字节计数。完成须满足全部文件字节已发送并收到合法完成回复，不能仅见 0x02 就报成功。
- 上传独占会话；超时、断线、取消后停止发送并清理资源，不自动重试整次上传。
- 上传后按索引查询 0x36 刷新唯一列表；不使用协议注明尚未实现的 FF 查询全部。

双列表继续使用现有 32768 字节分包、含列表 ID 的请求和状态 ACK 语义，厂家返回固定序号 2 的已验证行为不受影响。

厂家没有定义单列表 ACK 序号的重复、回绕和重发规则，不能照搬双列表的固定序号结论。初期不做包重传；不确定的 ACK、迟到回复和不符合状态的完成回复必须停止或超时失败，不推进后续包。精确序号策略以单列表设备抓包验证后确定。

## 视频处理复用与验证边界

复用现有视频选择、取景、裁剪、缩放、黑边、进度、取消和临时文件清理。单列表媒体流程从视频转换开始，绝不调用抽取音频接口，也不产生 MP3 上传任务。双列表日常列表继续现有音视频处理，蓝牙列表继续现有视频处理。

现有转换器内部输出专用 `video.bin`；双列表上传使用 `.mp4` 文件名不意味着文件是通用 MP4。转换器使用极坐标映射、JPEG 记录与专用容器。单列表通信文档只描述传输，未证明该容器能在单列表硬件播放。

因此把已有编码器作为复用候选，与传输文件名规则分开。单列表默认产品流程在编码兼容性验证前提示该机型上传尚待验证，不将候选编码当作已支持格式。测试构建可以输出候选文件用于硬件验证；只有传输和播放都验证后才开放普通用户上传。不会把普通视频改后缀当作转码。

另一个硬件验证门槛是末包：厂家未说明不足 35700 字节的末包是否允许，已有编码器的输出长度也不保证整除该值。未确认前不静默填充或截断；测试传输只接受长度符合已知规则的有效样本。需要厂家有效单列表文件或抓包确认末包规则，再完成任意长度文件上传。

这两个未确认项不阻塞连接、列表控制和无音频流程的实现，但阻塞“普通手机视频已经支持单列表播放”的交付结论。若验证不兼容，继续复用公共视频准备，仅替换单列表最终编码器；新增编码算法须有厂家格式依据，不能猜测。

## 改动边界

预计涉及 dashboard 的连接生命周期，device 下的设备类型、会话与单列表上传适配，video 下的媒体流程、上传入口、列表界面，以及设备设置的能力校验。
现有 `p20_ffmpeg_preparation.dart` 的公共视频处理、`p20_bin_encoder.dart` 的编码能力尽量复用。`p20_v2_connection.dart` 和已有双列表厂家帧测试作为保护边界，不为统一接口而改变其线序或 ACK 判定。

不改后台服务，不新增单列表音频能力，不重写双列表上传，不进行无关界面重构。

## 验证与验收

自动化验证覆盖：两种探测的原始帧及超时失败、手动选择校验、切换设备的旧回调隔离、单列表命令不带列表 ID、单列表无音频调用、包长和文件名限制、上传独占、取消和错误清理、列表刷新与不支持入口隐藏。测试使用独立的厂家示例或固定字节断言，不能用生产编码器生成全部期望值。

保留双列表四组厂家上传帧、32768 分包和固定 ACK 序号回归。新增流程后执行相关测试、完整 Flutter 测试、静态分析及 iOS 模拟器构建；现有跳过测试如仍跳过需报告。当前 Mac 未配置 Android SDK，不将 iOS 构建成功描述为 APK 构建或硬件验证成功。

实机验收分别记录：
1. 双列表连接、两个列表、音视频处理和短视频上传均与原版本一致。
2. 单列表连接和唯一列表控制正确，没有音频处理或上传。
3. 单列表厂家有效样本完成传输并可播放，确认末包规则。
4. 现有编码器生成的短视频在单列表上画面、方向、颜色、时长正确；无声音步骤。
5. 断线、取消及更换硬件后不显示旧状态，不误报成功。

只有第 3、4 项均通过，才将单列表普通视频上传标记为可用。设计确认后的下一步是形成逐项实施计划，再进入代码实施。
